## CI E2E execution

**PASS.** New `e2e` job in `.github/workflows/ci.yml`, `needs: [backend, frontend]`, its own isolated Postgres service container, installs Chromium with OS dependencies (`--with-deps`), runs `npm run test:e2e`, uploads the Playwright report/traces as a workflow artifact on failure.

Local CI-equivalent simulation (fresh ephemeral Postgres container on an unused port, `CI=true` env — disables `reuseExistingServer` and enables `retries: 1`, matching real CI exactly): **first attempt failed all 8 tests** with browser-reported CORS/`ERR_FAILED` errors. Root-caused (not just retried): `backend/scripts/e2e_server.py` called `app.core.config.get_settings()` once to derive its default database URL, *before* finishing setting up the `DATABASE_URL` env var override -- `get_settings()` is process-wide `@lru_cache`'d, so that one early call permanently cached a `Settings` instance pointing at the *original* (dev) database for the rest of the process's life, including for uvicorn itself once it started. Fixed by reading the raw `DATABASE_URL` env var directly instead of calling `get_settings()` for that computation. Re-ran the identical CI simulation afterward: **8/8 pass**, including the GitHub Actions annotation reporter (`::notice title=🎭 Playwright Run Summary::`) confirming the `github` reporter config works.

**This bug's blast radius was larger than the CI simulation alone revealed, and is reported here in full rather than minimized.** The identical caching defect affected *every* local E2E run made before the fix, including ones against the normal local dev Postgres (not just the ephemeral CI-simulation container) — because the affected code path (`get_settings()` returning the wrong, unswapped database and the wrong, unset storage root) doesn't depend on which Postgres instance is listening. Direct inspection after the fix confirmed **27 real "E2E ..." project rows and 38 orphaned plan directories had been written into the actual dev database (`massiq`) and dev storage tree (`backend/app/storage/`)** during this session's pre-fix debugging, not into the intended isolated `massiq_e2e` database/temp storage root at all — the isolation this release exists to provide was silently not functioning for that whole period, and only local iteration happened to make this invisible (each run's `reuseExistingServer` reused one already-correctly-configured long-lived process from very early in the session, before enough env-var permutations had been tried to expose the bug). All 27 leftover projects and 38 orphaned storage directories were identified and deleted from the dev database/filesystem before this release's commit. Verified clean afterward: `SELECT count(*) FROM projects` → 0 in the dev database; `backend/app/storage/plans/` → empty. Post-fix, a local (non-CI) run against the normal dev Postgres was re-verified to correctly isolate to `massiq_e2e` (confirmed via direct `psql` inspection of both databases' row timestamps).

## Bugs found and fixed by this release

Building this suite for real (not just writing specs that were assumed to pass) found **four genuine, previously-unknown bugs**, none caught by the existing 193 backend+frontend unit tests:

1. **`PlanViewer.jsx` (legacy MVP) had the same undiscovered native-image-drag bug R3 already fixed in the new Legend workflow.** Same root cause (`<img>` draggable by default), same one-line fix (`draggable={false}`), found only because R3.5 was the first time this specific legacy interaction was driven by a real browser instead of a person's mouse in ad hoc manual testing.
2. **`PlanViewer.jsx` hardcoded `backendBase = 'http://127.0.0.1:8010'`**, ignoring the `VITE_API_BASE_URL`/`VITE_BACKEND_URL` environment configuration every other API call in the app already respects (`src/api/api.js`). Invisible in normal local dev (the backend genuinely runs on 8010 there); a silent, total image-load failure the moment the app runs against any other backend port — exactly what an isolated E2E backend does. Fixed by defaulting to `api.defaults.baseURL` instead of a second hardcoded value.
3. **A real React race in `LegendEntryEditor.jsx`.** Two separate `useEffect`s could both fire on the same "load a different entry" render — one seeding `correctedText` from `entry.corrected_text`, the other (intended only for "OCR just completed on the same entry") seeding from `entry.raw_ocr_text` — and because both read the same pre-render `correctedText` closure value, the second silently overwrote the first's correct value. Practical effect: reloading the page and reopening an already-confirmed LegendEntry displayed the raw OCR text instead of the saved, human-corrected text. Caught by `persistence.spec.js`'s very first run; fixed by collapsing both effects into one, ref-tracked branch (`loadedEntryIdRef`) that distinguishes "a different entry just loaded" from "the same entry's OCR just completed."
4. **Vitest was also collecting Playwright's E2E spec files** (see "Frontend unit suite" above) — a build/tooling gap, not an application bug, but a real gap this release closed.
5. **`e2e_server.py` itself (this release's own new infrastructure) cached the wrong database URL on a genuinely fresh cold start** — see "CI E2E execution" above for the full account. Found only by a real CI-equivalent simulation (fresh Postgres, `CI=true`, no server reuse), not by any of the many successful *local* runs that preceded it, since those had all been silently reusing one already-correct long-lived process. A reminder that "it works when I run it locally" and "it works from a genuinely clean, fresh start" are different claims, and only the second one is what CI actually promises.

None of these were hypothetical or contrived for this release — every one was discovered by a spec or a CI-equivalent simulation genuinely failing on a real run, then root-caused and fixed the same way a real production incident would be.

## Reproducibility from a clean checkout

**PASS (with one noted limitation).** No absolute machine-specific paths anywhere in the E2E infrastructure: `frontend/e2e/scripts/start-backend.js` resolves the backend's Python interpreter relative to the repo root, preferring a local `.venv` if present (local dev) and falling back to plain `python` on PATH otherwise (matching exactly how the existing `backend` CI job installs dependencies, with no venv). This fallback branch's logic was verified by code inspection; it was not exercised end-to-end in this environment, since only one Python installation (the project's own `.venv`) was available to test against locally. The `e2e` CI job (no venv on a fresh runner) is the first real exercise of that branch — flagged honestly rather than assumed.

## Risks before R4

- The four bugs found and fixed here were all in *existing* R1–R3 code, not in this release's own new infrastructure — a healthy sign for R3.5 itself, but a reminder that the backend+frontend unit-test baseline alone was not sufficient evidence of a working product, even though every one of those 193 tests was genuinely passing the whole time. Any future release should budget for at least one real E2E run before considering a feature "done," not just unit/integration coverage.
- E2E run time (~30-60s locally for the full 8-scenario suite, including two full Postgres migrate-from-empty cycles at webServer startup) is fine today; if R4+ substantially grows the number of E2E scenarios, revisit the "serial, one worker" decision before it becomes a CI bottleneck.
- No cross-browser evidence exists yet (Chromium only) — acceptable per this release's explicit scope, but a real gap if the product ever needs to support Firefox/Safari users with confidence.
